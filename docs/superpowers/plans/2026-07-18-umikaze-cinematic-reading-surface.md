# 海風 — 商業ノベルゲームとしての読書面へ戻すための再設計計画

**状態:** 調査・設計確定前  
**対象:** `examples/umikaze/ui` の React/Tauri プレゼンテーション。物語 VM、セーブの意味論、ローカライズ、入力契約は維持する。  
**非目標:** 特定作品の画面、素材、ロゴ、文言を複製すること。ここで採るのは画面の役割分担と演出上の原理だけである。

## 0. 結論

海風は「モダンな Web アプリ」ではなく、**静かな映写室で読む商業 ADV** にする。

現在の画面には、慎重に作られた色と文字がある一方で、常設のヘッダー、右上のテキストボタン、全幅の情報帯、均一なカード、右／下から出るシートが同時に見える。これは便利なアプリケーションの文法であり、読む前に「操作している」と感じさせる。問題は藍色や金色の選択ではなく、UI が物語より先に自己紹介することにある。

再設計の一文は次である。

> 画面の既定状態は風景と文だけ。機能は必要な瞬間に、物語世界の余白として現れ、終われば痕跡を残さず退く。

ホーム／タイトルの左寄せ情報レールは、既にこの方向を最もよく満たしている。捨てない。読書面、選択肢、rmenu、記録画面を同じ節度まで引き上げる。

## 1. 何を研究したか

### 1.1 ナルキッソス — 「少なさ」を演出として使う

* `narcissu 1st & 2nd` は Stage-nana の kinetic novel で、NScripter 系の作品として配布されている。[SteamDB の作品情報](https://steamdb.info/app/264380/screenshots/)
* 批評・プレイ記録が共通して指摘するのは、狭い表示領域、限られた情景、クリック／自動送り中心の入力である。[Reikaze Rambles の分析](https://reikazerambles.com/posts/rockmandash-reviews-narcissu-1st-2nd-visual-novel-1676683203/) は「世界を見せる窓を小さくする」ことが視点と感情に接続していると読む。[別のプレイ記録](https://pages.cs.wisc.edu/~linzuo/deliverables/stage1/steam/steam2954.html) も、選択をほとんど置かず、映画／読書に近い進行を説明している。
* ここから採る原則は「古い狭窓の見た目」ではない。**情報を減らした理由が物語の距離感と一致していること**である。海風なら、海辺の風景を広く残し、文を低い位置に置き、メニューを常駐させない。静止と空白を予算として扱う。

### 1.2 銀色と古典的商業 AVG — 機能は多くても、読書中は前面に置かない

* `銀色 -完全版-` の当時のシステム評では、オート、イベント再生などの標準 AVG 機能を備えることが評価され、画面効果の強化が別軸として語られている。[当時のレビュー](https://www2u.biglobe.ne.jp/~fau/hobby/game/giniro.htm)
* 教訓は、機能の少なさではなく**機能の居場所**である。セーブ、ロード、既読スキップ、バックログ、コンフィグは読書を壊さず必ず届くが、台詞より目立たない。
* 旧 C# 版もこの系譜にある。`rmenu` は SAVE / LOAD / BACKLOG / SKIP / CONFIG / RESET / QUIT を持ち、設定には BGM、SE、文字速度、オート待ち、未読スキップ、クリックカーソル、フルスクリーンがある。根拠は [`src/AriaEngine/assets/scripts/main.aria`](../../../src/AriaEngine/assets/scripts/main.aria) と [`settings_ui.aria`](../../../src/AriaEngine/assets/scripts/settings_ui.aria)。V3.2 の見た目が変わっても、これは削ってよい機能一覧ではない。

### 1.3 現行商業ノベル — 文脈別に UI 密度を切り替える

* Key の [Summer Pockets 公式ギャラリー](https://key.visualarts.gr.jp/summer/gallery.html) と現行版の配信画面は、情景・立ち絵・台詞を主面に置き、保存／既読／自動などを補助面へ退かせる ADV の実例になる。[Steam 作品ページ](https://store.steampowered.com/app/3418570/Summer_Pockets_REFLECTION_BLUE/) も、複数言語のインターフェースと音声・字幕を同時に扱う商業上の条件を示す。
* [ATRI の公式配信ページ](https://store.steampowered.com/app/1230140/ATRI_My_Dear_Moments/) は、海と夏を主題にした商業ノベルが、背景・人物・文字の三層を明確に扱う比較対象である。海風はそこから「海色の UI」を真似るのではなく、**背景の情緒を UI が食い潰さない**という優先順位を採る。
* UI 資料アーカイブは、標準的な下部テキストボックスの **ADV** と、画面全体を文章に使う **NVL** を別の型として扱う。[Visual Novel Interfaces の分類](https://visual-novel-interfaces.tumblr.com/what) 海風は通常は ADV、回想・章扉・手紙では限定的 NVL に切り替える。全画面を同じ「アプリのパネル」にしない。

### 1.4 横断的なゲーム UI の示唆 — UI を世界の外側にしない

Metaphor: ReFantazio の UI 設計者は、UI をゲーム世界から切り離されたメタ機能ではなく、プレイヤーと世界をつなぐ要素として扱う方針を語っている。[GDC 2025 の報道](https://www.gamesradar.com/games/jrpg/the-lead-ui-designer-on-metaphor-refantazio-had-never-designed-for-a-game-before-he-just-rolled-up-and-made-some-of-the-best-ui-ive-ever-seen-in-a-jrpg/) 海風では派手なメニューを輸入しない。代わりに「記録」「余白」「潮目」という作品内の語彙だけで、機能画面を世界に接続する。

## 2. メタ認知: 現行案をなぜ「Webゲーム」に感じるのか

これは好みの否定ではなく、視覚的原因の切り分けである。

| 現行の選択 | 画面上の作用 | なぜ Web 的に読むか | 再設計での扱い |
| --- | --- | --- | --- |
| 常設の作品名・履歴・メニューボタン | 読書面の上端を常に UI が占める | アプリの global navigation に見える | 平時は消す。キーボードフォーカス時、ポインタが端に来た時、または明示操作時だけ出す。 |
| 下端いっぱいの濃い `reading-band` | 画面を風景とパネルに二分する | SaaS の固定フッター／チャット欄に近い | 台詞のための局所的な読書領域に縮める。地の文はより薄く、話者の文だけ必要量を保護する。 |
| 一律のカードと 2×N グリッド | 情報がすべて同じ重さになる | ダッシュボード、管理画面の視覚文法 | 章・セーブ・CG は情報の役割ごとに違う構図にする。 |
| 右側／下側の同型シート | 機能を「設定パネル」として見せる | Web の drawer / bottom sheet を連想する | 画面種別ごとに余白・選択・復帰の設計を変える。 |
| `READING`、`RECORDS`、`ON`、連番を多用 | メタ情報が本文より視覚優先される | 管理ツールのラベル体系に近い | プレイヤーが判断に必要な語だけを残す。連番は実際に順序が意味を持つ場所だけで使う。 |
| 全画面 CSS filter / backdrop-filter と隠れた WebGL canvas | 静止画面でも合成負荷が残る | 体感の鈍さが「WebView の画面」に直結する | 焼き込み済み／軽量な色調整と、表示されない描画経路の停止に置き換える。 |

現行の良い点も保持する。

* タイトルの左レール、海辺の写真、静かな色相、可読性を優先した文字サイズ。
* rmenu の全機能、セーブ世代、バックログ、章・CGの進捗、ローカライズ、キーボード／ゲームパッド／タッチ、AccessKit。
* reduced motion と high contrast の選択肢。新しい静けさは、到達不能な静けさではない。

## 3. アートディレクション

### 3.1 呼び名: **潮の余白 (Tide Margin)**

海風の UI は「海の装飾」ではなく、旅の途中で残した紙片・海図の欄外・車窓に重なる反射である。水滴、波、砂、金箔、グラスモーフィズムを大量に置かない。固有のサインは一つだけにする。

**サイン:** 台詞または選択中の項目にだけ現れる、短い銀灰色の「潮位線」。これは下線でも進捗バーでもなく、現在プレイヤーが読んでいる行の手前に置かれる 1 px の水平線である。

### 3.2 トークン

| 役割 | 名称 | 値 | 使用箇所 |
| --- | --- | --- | --- |
| 深い基底 | `ink-water` | `#08171F` | 夜景・メニューの暗部。広面積では不透明度を抑える。 |
| 霧の紙 | `fog-paper` | `#E7ECE8` | 本文・高コントラスト本文。純白を常用しない。 |
| 退いた文字 | `salt-grey` | `#AEBDBB` | 作品名、補助情報、未選択の機能。 |
| 海図の線 | `tide-silver` | `#839A9D` | 潮位線、薄い境界、フォーカス以外の輪郭。 |
| 灯り | `late-gold` | `#B59B66` | 現在位置、確定、再生中。ひとつの画面で一箇所を原則にする。 |
| 注意 | `faded-rust` | `#A56D64` | 終了／破棄確認だけ。通常アクションには使わない。 |

色で状態を伝え切らない。フォーカスは 2 px 輪郭＋潮位線、選択は位置・線長・太さ、無効はラベルと操作不可状態で示す。

### 3.3 文字

* **本文／章扉:** 配布フォントとして Noto Serif JP（OFL の静的サブセット）を導入し、OS の明朝フォールバックに体験を委ねない。本文は 18–23 px 相当、行高 1.9–2.05、字間は 0–0.025em。読み味を優先し、軽い／細いウェイトを濫用しない。
* **機能名／数値:** Noto Sans JP。10–13 px 相当、必要な局面だけ letter-spacing を使う。すべてを英字小見出しにしない。
* **英中韓:** 文の言語に応じた行長を実測し、同じ固定高さで切らない。翻訳文はデザインの余白を借りず、コンポーネントが伸びる。

### 3.4 動き

動きは「常にある雰囲気」ではなく、視点が切り替わる合図である。

* 章開始: 写真が 180–260 ms で露出し、章題が一度だけ 120 ms で現れる。
* 台詞: 文字送りだけ。本文パネル全体を毎回 slide-in しない。
* メニュー: 120–160 ms の短い暗転または余白の展開。blur、弾む spring、無限 loop、視差、hover でのカード拡大を使わない。
* CG／回想: フェードの後に静止する。画面が止まること自体を演出とする。
* reduced motion: すべて即時遷移。情報構造は変えない。

## 4. 画面ごとの実装仕様

### 4.1 読書面（最優先）

```
┌──────────────────────────────────────────────────────┐
│                                                        │
│                     scene / CG                         │
│                                                        │
│                                                        │
│  （端にポインタ／Tab 時だけ補助操作）                     │
│                                                        │
│      ─────  瀬津美                                    │
│      風の向きが、少しだけ変わった。                       │
│      次の駅まで、まだ時間がある。                         │
│                                                   ·    │
└──────────────────────────────────────────────────────┘
```

* **既定:** 本文以外は存在しない。画面左上の作品名、右上の履歴／メニューを常設しない。
* **台詞:** 幅は画面の 54–62% を上限にし、下端から 10–14% 上げる。黒い全幅帯ではなく、本文の背後だけに 8–30% の暗い露出保護を置く。明るい背景では local gradient を増し、暗い背景では消す。
* **地の文:** 話者名を出さない。必要時だけ NVL 寄りの中央縦組みではなく、中央寄りの狭い読み幅へ切り替え、画面を文章へ譲る。
* **続き印:** 点または小さな短線を一度だけ出す。下向き矢印の常時表示・点滅は行わない。
* **操作の入口:** 右クリック、Esc、ゲームパッド Menu、明示的にフォーカスした `メニュー`。マウス移動で上端へ出す補助クロームは 2 秒で退避する。タッチでは 44 dp の透明でない、低コントラストな固定ホットスポットを右下に設ける。
* **本文を隠す選択:** 将来的に `H` またはタップで本文を消せる。読む／眺めるをプレイヤーが切り替えられることは、没入を壊さない。

### 4.2 選択肢

```
                ─  行かない
                  もう少し、ここにいる
                  彼女の名前を呼ぶ
```

* 通常選択はカードにしない。本文の読み幅に揃えた 1 列で、1 行 48 dp 以上の行間を確保する。
* 選択中は潮位線が伸び、文字がわずかに明るくなる。ホバーだけで拡大／反転しない。
* 章選択など「選ぶ対象そのものが作品のまとまり」の場合だけ、大きな視覚面を使う。すべての choice に同じカード部品を適用しない。
* キーボードとゲームパッドでは現在行を必ず明示し、音なしでも選択が分かる。

### 4.3 rmenu — **中断の余白**

```
                         ───────────────
                         読む
                         オート       スキップ

                         記録
                         セーブ       ロード       履歴

                         環境
                         設定

                         ───────────────
                         タイトルへ                 終了
```

* 現行の「右下に置かれた大きな ledger」は、情報設計としては正しいが、箱・見出し・フッターが揃いすぎてアプリのダイアログに見える。
* 広域では画面右 30% の**無枠の余白**に文字を置く。背景は必要量だけ 65–78% 暗くする。外周の枠、drop shadow、backdrop blur は使わない。
* 狭域では下から出るが、カードの角丸ではなく画面下端から続く「本文の余白」にする。復帰操作は最初の行で 44 dp。
* 見出しは残すが、英字の `READING` を装飾として使わない。日本語なら「読む」「記録」「環境」、ローカライズごとに自然な短語にする。
* 機能は従来どおり SAVE / LOAD / BACKLOG / AUTO / SKIP / CONFIG / RESET / QUIT。追加で触覚的に分かる「今オート中」を文字と潮位線で示す。

### 4.4 セーブ／ロード — **記録台**

* サイドシートをやめ、風景の露出を落とした全画面記録面にする。大画面は 2 列×5、狭域は 1 列。
* 各スロットには、番号ではなく `章題 / 直近の話者または本文抜粋 / 保存日時 / 小さな場面断片` を置く。未保存は「空の記録」ではなく、同じ高さの静かな空欄にする。
* 現在の semantic save に preview/date がないなら、保存 envelope から安全に抽出するか、保存ストアのメタデータを拡張する。サムネイルのために画面をキャプチャする設計は、低 FPS と可搬性を悪化させるため最初の版では採らない。
* 読み込み確認と上書き確認は、対象スロットの近くに出す。中央に別モーダルを重ねない。

### 4.5 バックログ — **読み返し**

* 1 行ずつのカード列ではなく、左余白に番号、右に話者と本文を置く長い組版にする。
* 現在行は左の潮位線だけで示す。ボタンの面積は十分に保ち、視覚上の境界線は最小にする。
* 読書面に戻る時は、同じ文章の位置関係を保って fade out。シートを横へ飛ばさない。

### 4.6 設定 — **調律**

* 完全な新画面として扱い、スライダーは 1 つずつ広く見せる。BGM / SE / voice、文字速度、オート待ち、文字サイズ、未読スキップ、クリックカーソル、フルスクリーン、コントラスト、動きの抑制を漏らさない。
* 既存の説明のない `ON`／`OFF` を、状態名とスイッチの両方で伝える。スライダーは矢印キー／ゲームパッドで 1 step、PageUp/Down で大きく動く。
* `保存しました` のトーストを出し続けない。設定は即保存し、必要なら画面下端の短い非侵襲メッセージだけにする。

### 4.7 章選択 — **章扉の連なり**

* 2×4 の同型カードから、「現在の章を大きく、過去を静かに、未到達を遠く」へ変える。
* 大画面: 左に選択中の章題と短い導入、右に細い縦の章目次。狭域: 上に選択中、下に縦目次。
* 進捗は % 表示を前面に出さない。既読／未読／完了を、章題の明度・潮位線・短い補助語で表す。数値がプレイヤーの判断に必要な場合だけ表示する。

### 4.8 CG ギャラリー — **写真箱**

* グリッドは維持するが、すべてを hover で拡大・filter しない。固定の露出と一つの選択状態だけにする。
* ロック中は単なる灰色フィルターでなく、題名のない紙片／余白として扱う。何を取り逃したかを過剰に示さない。
* 一覧→詳細は、場所を変えるのではなく同じ写真が静かに前面へ出る。連続的なパララックスを使わない。

### 4.9 タイトル／初回言語選択

* 現在のホームの左情報レールは保持する。タイトル画面は「一覧メニュー」へ寄せず、最初に海の景色と作品名を読ませる。
* 言語選択は四枚のカードではなく、同じ本文幅の四行にする。自言語名＋短い言語名だけで十分。選択後は一回の fade でタイトルへ移る。

## 5. 実装アーキテクチャ

### 5.1 画面責務

```
Aria/WASM semantic view model
          │
          ├── story state / save state / settings / input intents
          │
React presentation
          ├── Stage: 写真、露出、章ごとの静止背景
          ├── ReadingSurface: 台詞／地の文／選択肢
          ├── QuietChrome: 必要時だけ現れる補助操作
          ├── Interruption: rmenu
          └── Archive: save/load/backlog/settings/chapters/gallery
```

* Aria の UI DSL や旧 VM 直描画に戻らない。現在の semantic contract と React/React Aria のアクセシブルな部品を使う。
* `App.tsx` を一枚の巨大な画面 switch に成長させず、上の責務ごとにコンポーネント／CSS レイヤーを分ける。
* `Stage` は scene color を単に写真へ対応させる暫定マップから、章・場面ごとの `StageCue` へ昇格する。`StageCue` は画像、位置、露出、局所暗幕、章扉の可否だけを持つ。連続 shader を持たない。
* UI 状態は semantic save に残す。アニメーションの途中座標、hover、CSS の一時状態は保存しない。

### 5.2 保存メタデータの不足を埋める

現行 React の save card はスロット番号と操作名しか知らない一方、旧 UI は `saveinfo` の本文抜粋と日時を表示していた。

1. save command 実行時に、現在の chapter id、speaker、全文の安全な短縮、timestamp を `SaveGeneration` のメタデータとして保存する。
2. `UiViewModel` へ表示専用の `save_slots` を追加する。load 可否は既存 action contract のまま保持する。
3. 旧セーブはメタデータなしとして正常にロードし、UI では「以前の記録」と表示する。移行不能にしない。

### 5.3 パフォーマンスの設計原則

* 実際に見えない WebGL/WebGPU canvas を作成・submit しない。umikaze の Stage は React の写真層なので、WASM scene renderer はこの presentation では no-op にする。
* ネイティヴ版が毎回 debug WASM を梱包している経路を廃止し、`aria-web` と `aria-cli` を release でビルドして Tauri bundle に入れる。
* 全画面 `filter`、`backdrop-filter`、常時の blur、無限 animation を削る。写真の露出は軽い overlay または事前調整済みアセットで作る。
* 物語の更新だけを requestAnimationFrame で 60 Hz に publish する。静止画面、完了済み台詞、オートでもない待機画面は timer も draw も行わない。
* renderer の有無に応じて scene fingerprint の `JSON.stringify` を行わない。表示しないフレームの比較・GPU submit はゼロにする。

### 5.4 計測の受け入れ条件

| 条件 | 合格基準 | 測り方 |
| --- | --- | --- |
| 静止読書面 | 5 秒間に scene renderer submit 0 回、継続 rAF 0 回 | runtime counter と Playwright。 |
| 文字送り | 1280×720 の native/Web で frame interval p95 ≤ 20 ms | 開発時のみ frame-pacing probe を有効化。 |
| 操作 | クリック／キー入力から semantic output の反映まで次の frame | intent timestamp を debug build で記録。 |
| ネイティヴ idle | 同一環境・同一画面で変更前より WebKit CPU と wakeup 数が有意に低い | 5 秒×複数回の process sample。絶対 % は GPU/WM に依存するため比較値を残す。 |
| 移行 | rmenu の旧機能、保存、ロード、既読スキップ、バックログ、設定、章、CG、ローカライズ、AT が通る | Playwright + native manual/AT-SPI test。 |

## 6. 段階的な実施順

1. **パフォーマンスの土台を直す。** release WASM、DOM stage の no-op renderer、filter/blur の撤去、typing publish を rAF に揃える。見た目を大きく変える前に体感を安定させる。
2. **読書面だけを作り直す。** 常設 chrome を退避し、台詞・地の文・選択肢を Tide Margin の構図に置く。ここが通らなければ他画面を装飾しない。
3. **rmenu と settings を作り直す。** 中断の余白と調律画面へ変え、旧設定項目の欠落を埋める。
4. **記録・読み返し・章・写真箱を別々に作る。** 同型カード／シートの共通化を意図的に解く。save metadata contract もこの段階で導入する。
5. **タイトルを最終調整する。** 現在よい部分を残し、初回言語選択と章扉を同じ密度に揃える。
6. **批評→削除→再検証。** 画面ごとに「これは他の Web アプリにもそのまま使える装飾か」を問い、Yes なら削るか作品固有の機能へ置き換える。アニメーションも同じ基準で一つずつ削る。

## 7. 実装前チェックリスト（毎画面）

* これは物語のどの瞬間に必要な画面か。読書を中断する理由はあるか。
* 画面にある線・番号・英字・金色は、情報を伝えているか、それとも「それらしく」しているだけか。
* 背景を暗くする必要は本文を読むためか、パネルを目立たせるためか。
* 通常状態で UI を隠しても、キーボード、ゲームパッド、タッチ、スクリーンリーダーから同じ操作へ届くか。
* その動きは場面転換を伝える一回の動きか、静かな画面に負荷と注意を足しているだけか。
* これは海風の「記録」「潮目」「旅」のいずれかと結びつくか。結びつかなければ削る。

このチェックを通ったものだけを実装する。デザインを増やすことではなく、物語の存在感を増やすことが成功条件である。
